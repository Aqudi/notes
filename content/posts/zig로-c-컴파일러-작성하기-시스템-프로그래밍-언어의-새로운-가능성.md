## Zig로 C 컴파일러 작성하기: 시스템 프로그래밍 언어의 새로운 가능성

C언어는 여전히 운영체제, 임베디드 시스템, 데이터베이스 등 현대 IT 인프라의 든든한 기반이지만, 오늘날에도 여전히 메모리 안전성 부족과 antiquated(구시대적인)한 빌드 도구라는 한계를 안고 있습니다. 최근 [[메모리 안전성]]이 소프트웨어 보안의 핵심 이슈로 떠오르며 [[Rust]]가 큰 주목을 받고 있지만, 가파른 학습 곡선과 기존 C 생태계와의 상호 운용성 한계는 여전히 많은 개발자에게 진입 장벽으로 작용합니다.

이러한 배경 속에서 강력한 대안으로 부상하고 있는 것이 바로 **"더 나은 C(Better C)"** 철학을 가진 **[[Zig]]**입니다. **Zig는 가비지 컬렉션(GC)과 복잡한 매크로 없이도 뛰어난 성능과 메모리 안전성을 제공하는 현대적인 시스템 프로그래밍 언어입니다.**

Bun 런타임이나 Tigerbeetle 금융 DB 등에서 그 성능을 입증한 Zig는, 과연 C언어를 대체할 만큼 저수준 제어력과 안전성을 갖췄을까요? 이 질문에 대한 가장 확실한 답은 **"Zig로 C 컴파일러를 직접 작성해보는 것"**입니다. 

이번 포스트에서는 Zig를 활용해 C 컴파일러를 작성하는 과정을 통해 시스템 프로그래밍 언어의 새로운 가능성을 탐구해 보겠습니다.

---

### 1. 왜 하필 C 컴파일러를 Zig로 작성하는가?

컴파일러는 언어의 저수준 제어能력을 극한으로 시험하는 프로젝트입니다. Zig는 태생적으로 C의 [[ABI]](Application Binary Interface)와 완벽하게 호환되도록 설계되었습니다. 별도의 바인딩 파일(FFI) 없이도 C 헤더를 직접 임포트하고 호출할 수 있는 것은 컴파일러 개발에 엄청난 이점을 줍니다.

또한, Zig는 [[크로스 컴파일]]이 기본적으로 내장되어 있습니다. 작성한 컴파일러를 x86_64뿐만 아니라 ARM, RISC-V 등 다양한 타겟 플랫폼으로 빌드하고 테스트하는 과정이 매끄럽게 이루어지며, 이는 임베디드나 IoT 개발자들에게 강력한 무기가 됩니다.

### 2. 메모리 관리와 AST 설계: `ArenaAllocator`의 힘

가비지 컬렉터(GC)가 없는 환경에서 컴파일러를 작성하는 것은 꽤나 까다로운 일입니다. 컴파일러는 파싱 과정에서 수많은 토큰과 노드를 생성하는데, Java나 C#처럼 GC에 의존할 수도, Rust처럼 변수의 수명(Lifetime)을 일일이 추적해야 하는 것도 부담스럽습니다.

Zig는 명시적인 할당자(Allocator) 패턴을 통해 이 문제를 우아하게 해결합니다. 특히 컴파일러의 핵심 자료구조인 [[AST]](추상 구문 트리)를 관리할 때 `ArenaAllocator`를 사용하면 파싱 단계가 끝난 후 메모리를 한 번에 해제할 수 있어 성능과 안전성을 동시에 잡을 수 있습니다.

```zig
var arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);
defer arena.deinit(); // 블록이 끝날 때 할당된 모든 메모리를 한 번에 해제

const allocator = arena.allocator();

// 파싱 과정에서 생성되는 수많은 AST 노드들을 개별적으로 해제할 필요가 없음
const node = try allocator.create(AstNode);
node.value = 42;
```

### 3. 컴파일 타임 메타 프로그래밍: `comptime`의 마법

C 컴파일러를 작성할 때 복잡한 매크로나 코드 제네레이터에 의존해야 했던 영역을 Zig의 `comptime` 키워드로 완벽히 대체할 수 있습니다. `comptime`은 컴파일 타임에 코드를 실행하여 그 결과를 상수로 내장하는 강력한 기능입니다.

예를 들어, C언어의 토큰을 분석하는 파서에서 연산자 우선순위를 다룰 때, 이를 `comptime`에 미리 계산해 두면 런타임 오버헤드를 0으로 만들 수 있습니다. 유명한 파싱 기법인 Pratt Parsing을 구현할 때, 연산자의 바인딩 파워(Binding Power)를 `comptime` 테이블로 생성해 두면 런타임에는 복잡한 조건문 분기 없이 즉각적인 토큰 분류가 가능해져 파싱 성능이 극대화됩니다.

```zig
const std = @import("std");

// comptime에 평가되어 런타임에는 오직 결과 상수만 남음
fn prefixBindingPower(comptime op: u8) [2]u8 {
    return switch (op) {
        '+', '-' => .{0, 0}, // 단항 연산자 우선순위
        '*', '/' => .{1, 1}, // 곱셈/나눗셈 우선순위
        else => .{0, 0},
    };
}
```

### 4. 백엔드 연동과 실무 사례: `aro` 프로젝트

파싱된 C 코드를 실제 기계어로 번역하는 백엔드 단계에서 Zig는 LLVM에 대한 의존성을 줄이는 방향으로 진화하고 있습니다. Zig의 내장 백엔드(Backend)가 점차 안정화되면서, 무겁고 복잡한 C++ 기반의 LLVM 인프라에 의존하지 않고도 가벼운 크로스 컴파일 빌드 환경을 구축할 수 있게 되었습니다.

이러한 흐름 속에서 Zig 생태계의 핵심적인 실무 사례로 꼽히는 것이 바로 **[[aro]]** 프로젝트입니다. aro는 순수하게 Zig로 작성된 C 컴파일러 프론트엔드 및 전처리기 라이브러리입니다. 처음에는 Zig 자체의 C 번역 기능(translate-c)을 개선하기 위해 탄생했지만, 현재는 C 언어의 복잡다단한 문법과 매크로를 완벽하게 파싱하고 처리하는 수준까지 발전했습니다.

aro 프로젝트는 Zig가 단순히 'C를 대체하는 언어'를 넘어, 'C의 영역을 깊이 이해하고 소화할 수 있는 생태계'를 구축하고 있음을 방증합니다. 이처럼 Zig로 작성된 컴파일러 프론트엔드는 Zig의 자체 백엔드나 다른 백엔드들과 손쉽게 연동될 수 있어, 컴파일러 개발에 있어 막강한 유연성을 제공합니다.

### 결론: 시스템 프로그래밍의 미래와 Zig

지금까지 살펴본 것처럼 Zig로 C 컴파일러를 작성하는 과정은 언어의 저수준 제어 능력을 가장 극단적으로 시험하는 작업입니다. 명시적인 메모리 관리를 통한 안전성 확보(`ArenaAllocator`), 컴파일 타임 코드 실행을 통한 오버헤드 제거(`comptime`), 그리고 번거로운 FFI 없이 완벽하게 호환되는 C와의 상호 운용성은 Zig가 가진 독보적인 강점입니다.

가비지 컬렉터의 부재로 인한 런타임 지연이나 복잡한 문법적 오버헤드 없이도, Zig는 현대 시스템 프로그래밍이 나아가야 할 방향성인 '성능'과 '안전성'의 균형을 훌륭하게 맞추고 있습니다. 

C 언어가 쌓아온 거대한 인프라 위에서 그 한계를 극복할 차세대 도구를 찾고 계신다면, Zig를 활용해 작은 컴파일러나 인터프리터를 직접 구현해 보시길 권해봅니다. 시스템 프로그래밍의 새로운 가능성을 직접 경험할 수 있을 것입니다.
