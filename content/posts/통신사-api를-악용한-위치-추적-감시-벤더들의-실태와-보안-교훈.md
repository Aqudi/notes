## 당신의 스마트폰은 어디에 있나요? 통신사 API를 악용한 보이지 않는 위치 추적

2018년, 미국 통신사 가입자 2억 명 이상의 실시간 위치가 영장 없이 외부인에게 노출되는 대형 사고가 발생했습니다. 해커가 고도의 해킹 기술로 통신사 내부망을 뚫은 것이 아니었습니다. 위치 데이터 브로커의 웹사이트에 있던 버그를 통해 통신사의 **합법적인 위치 조회 API**가 악용된 것입니다. 최근 보안 연구자들의 발표에 따르면, 이처럼 통신사의 시스템 간(Peer-to-Peer) API를 악용해 보이지 않는 위치 추적을 수행하는 감시 벤더(Surveillance Vendors)와 데이터 브로커들의 위협이 갈수록 심각해지고 있습니다.

과거에는 스팅레이(Stingray)나 IMSI 캐처 같은 물리적 위조 기지국 장비를 사용해야만 휴대전화의 위치를 추적할 수 있었습니다. 하지만 이제는 감시 벤더와 데이터 브로커들이 통신사망(Core Network)에 직접 접근하여 단말기의 위치를 실시간으로 조회하는 API를 남용하고 있습니다. 하드웨어 기반 해킹에서 **소프트웨어 API 남용**으로 패러다임이 넘어가는 이 시점의 실태와 보안 교훈을 짚어보겠습니다.

---

## 1. IMSI 캐처의 퇴조와 통신사 API 공격의 부상

IMSI 캐처를 운영하려면 값비싼 장비를 구입해야 하고, 표적으로 삼은 사람의 근처에서 물리적으로 장비를 돌려야 한다는 치명적인 제약이 있었습니다. 게다가 최신 스마트폰은 위조 기지국을 감지하고 차단하는 기능을 탑재하면서 이 방식의 효용성은 크게 떨어졌습니다.

이에 따라 감시 벤더들은 눈을 돌렸습니다. 통신사가 파트너사나 법 집행 기관에 제공하기 위해 내부망에 구축해 둔 위치 조회 API를 해킹하거나, 우회하여 접근하는 방식입니다. 이 방식은 장비가 필요 없고 전 세계 어디서든 인터넷만 통해 타겟의 위치를 추적할 수 있다는 점에서 감시 업계의 '만병통치약'처럼 여겨지고 있습니다.

## 2. 감시 벤더의 생태계: 권한 남용과 데이터 유출

문제는 이러한 막강한 권한을 가진 API가 어떻게 사적 탐정, 스토커, 심지어 국가 단위 해커들의 손에 들어가게 되었는지입니다. 핵심은 **'합법적인 권한의 남용'**에 있습니다.

*   **LocationSmart 사태 (2018):** 미국의 위치 데이터 브로커인 LocationSmart는 자사 웹사이트의 버그를 통해 API를 노출시켰습니다. 이로 인해 외부인 누구나 영장 없이 미국 내 주요 통신사 가입자 2억 명 이상의 실시간 위치를 조회할 수 있었습니다. 
*   **Securus Technologies:** 수감자 통화 서비스를 제공하던 이 회사는 통신사로부터 '경찰용' 위치 추적 API 권한을 넘겨받았습니다. 그러나 이를 웹 인터페이스로 만들어, 영장 없이도 사설 탐정이나 일부 경찰관이 개인의 위치를 마음껏 추적할 수 있는 도구를 제공하다가 큰 논란이 되었습니다.
*   **Circles:** NSO 그룹과 연관된 이 감시 벤더는 통신망의 구조적 취약점을 뚫고 API를 호출해 전 세계 정부 기관에 타겟팅된 위치 추적 서비스를 팔았습니다.

## 3. 기술적 원리: SS7 프로토콜과 GMLC는 어떻게 뚫리는가?

이러한 공격이 가능한 근본적인 이유는 전 세계 통신사가 메시지를 라우팅하기 위해 사용하는 **[[SS7 프로토콜]]**(Signaling System No. 7)이나 Diameter가 '절대적인 신뢰(Trust)'를 기반으로 설계되었기 때문입니다.

공격자가 글로벌 로밍 네트워크에 접속할 수 있는 권한(해킹 또는 결제를 통한 획득)을 얻으면, 통신사의 **GMLC(Gateway Mobile Location Centre)**에 위치 조회 메시지를 직접 보낼 수 있습니다. 

예를 들어, 공격자가 `ProvideSubscriberInfo` 같은 메시지를 보내면, GMLC는 이를 정상적인 로밍 요청으로 착각하고 기지국 정보(Cell-ID)를 바탕으로 단말기의 위도/경도를 반환합니다. 내부 쿼리 로직을 살펴보면 다음과 같은 형태일 수 있습니다.

```json
// 공격자가 통신망으로 보낸 조작된 위치 조회 요청 (SS7/Diameter 기반)
{
  "subscriberId": "TARGET_PHONE_NUMBER",
  "locationInfo": {
    "cellId": "13A4-B02",
    "trackingArea": "SEOUL-GANGNAM"
  }
}

// 통신사 API가 반환하는 실시간 위치 데이터 (삼각측량 적용 시 오차 수십 미터)
{
  "status": "SUCCESS",
  "location": {
    "latitude": 37.4979,
    "longitude": 127.0276,
    "accuracy": 25 // meters
  }
}
```

도심에 기지국이 밀집된 경우 삼각측량을 통해 오차를 수십 미터 내외로 좁힐 수 있으며, 통신사 API가 단말기의 내장 GPS 데이터를 직접 쿼리할 경우 오차는 수 미터 이하까지 떨어집니다.

## 4. '동의'의 실패와 API 보안의 교훈

이러한 생태계는 금전적 이익을 위해 통신사가 위치 데이터를 쉽게 넘긴 것도 문제이지만, 이용약관에 심어둔 '제3자 제공 동의' 항목이 제 역할을 하지 못했음을 보여줍니다. 사용자는 자신의 데이터가 스토커나 해커에게 팔려나갈 것이라고 결코 동의한 적이 없습니다.

보안 담당자와 개발자는 이 사태에서 **[[API 보안]]**의 중요한 교훈을 얻어야 합니다. 통신사의 API 사고는 "우리 내부망이나 신뢰할 수 있는 B2B 파트너가 호출하는 API니까 안전하다"는 경계 기반 보안 모델이 완전히 실패했음을 의미합니다.

### 🛡️ 개발자/보안 엔지니어를 위한 방어 체크리스트

이제 막연한 경고를 넘어, 시스템과 API를 설계하고 운영하는 담당자들이 오늘 당장 점검하고 적용해야 할 구체적인 방어 체크리스트는 다음과 같습니다.

*   **[ ] 상호 TLS(mTLS) 기반 제로 트러스트 적용:** 단순히 신뢰할 수 있는 IP 대역이나 내부망에서의 요청이라고 해서 허용하지 마세요. [[제로 트러스트 아키텍처]] 원칙에 따라 API를 호출하는 클라이언트의 인증서를 강력하게 검증하는 상호 인증(mTLS)을 적용해야 합니다.
*   **[ ] 엄격한 스코프 제한 및 최소 권한 원칙 적용:** 파트너사나 내부 시스템에 API 권한을 부여할 때, 데이터의 종류와 조회 범위에 대해 가장 낮은 권한(Principle of Least Privilege)을 부여하세요. 위치 데이터의 경우, 정확한 좌표 대신 동/구 단위로 축소된 데이터만 제공하도록 스코프를 시스템 레벨에서 강제해야 합니다.
*   **[ ] 동적 데이터 마스킹(Dynamic Data Masking) 도입:** 민감한 PII(개인 식별 정보)나 위치 정보 등은 응답 객체에 담기 전, API 게이트웨이나 데이터베이스 단계에서 마스킹 처리되어 권한이 없는 사용자에게는 원본 데이터가 보이지 않도록 설계해야 합니다.
*   **[ ] 이상 탐지 및 자동 차단 시스템 구축:** 특정 API 키나 계정에서 단시간에 너무 많은 위치 쿼리가 발생하거나, 평소와 다른 패턴의 요청이 감지될 경우 즉각 차단하는 속도 제한(Rate Limiting) 및 패턴 기반 방어 시스템을 도입하세요.

일반 사용자 역시 통신망 레벨의 위치 추적은 스마트폰의 위치 서비스를 꺼도 피하기 어렵다는 점을 인지해야 합니다. 민감한 취재나 사생활 보호가 필수적인 상황에서는 전원을 완전히 끄거나 추적을 방지하는 특수 OS가 탑재된 보조폰을 사용하는 물리적 통제만이 유일한 해결책일 수 있습니다.

결론적으로 API는 비즈니스를 연결하는 유용한 도구지만, 그 뒤에 숨겨진 맹점을 간과해서는 안 됩니다. 사용자의 동의를 방패로 삼는 과거의 방어적 태도에서 벗어나, 근본적인 시스템 구조를 고민하는 시대로 접어들어야 합니다. 이는 거대한 통신망은 물론 일반적인 웹/앱 서비스 전반의 [[모바일 보안 및 프라이버시]]를 지키기 위한 필수적인 과정입니다.
